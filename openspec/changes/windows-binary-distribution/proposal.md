# Proposal

## Why

The Devsy CLI validates and installs provider binaries from a `provider.yaml`
manifest. The release workflow (`.github/workflows/release.yml`) already builds
4-platform binaries (`linux/amd64`, `linux/arm64`, `darwin/amd64`,
`darwin/arm64`) and uploads each to a GitHub Release. But the manifest
`provider.yaml` only advertises linux and macOS, so a Windows user installing
the provider gets a download error similar to:

`download binaries: cannot download provider binary PROXMOX_PROVIDER, because no binary location matched OS windows and ARCH amd64`

The upstream `v0.2.0` release ships Windows binaries with asset names
`proxmox-provider-windows-amd64` and `proxmox-provider-windows-arm64`. The
manifest does not register those two assets, and its `linux`/`darwin` asset URLs
do not match the actual upstream release asset names (see design decisions).

## What Changes

- Add `windows/amd64` and `windows/arm64` binary entries to `provider.yaml.tmpl`
  (and therefore `provider.yaml`) so Windows is advertised.
- Add 4 platform entries total (linux amd64/arm64, darwin amd64/arm64, windows
  amd64/arm64), matching the 4-platform build matrix and the upstream release
  asset inventory.
- Point every binary entry at the corresponding upstream GitHub Release asset
  URL and its SHA-256 checksum (`proxmox-provider-{os}-{arch}`).
- Add real upstream asset checksums for the new windows binaries (generated by
  the release workflow from `sha256sum`; they are stored as `.sha256` files in
  `dist/` and the workflow uploads them as assets). They are once-off
  build artifacts, so this change documents their expected checksums and the
  release workflow produces them deterministically at publish time.

## Capabilities

### Modified Capabilities

- `proxmox-provider-distribution`: Manifest now advertises windows/amd64 and
  windows/arm64 and references the upstream Windows Release assets.

## Impact

Affected areas:

- `provider.yaml.tmpl` — add windows binary entries.
- `provider.yaml` — generated manifest; add windows entries (generated from the
  template at release time; the template is the source of truth).
- `.github/workflows/release.yml` — no change required for the manifest
  generation; it already derives URLs from `github.repository` and the build
  matrix covers 4 platforms.
- `README.md` / docs — optional; distribution instructions read the manifest,
  but any pinned Windows docs should reference the new asset URLs.

## Non-Goals

- Changing the build matrix size (4 platforms stays).
- Fixing Proxmox provider runtime behavior.
- Publishing a new tag/release (the release workflow handles that when a tag
  is cut).
